## 1. Субъектно-объектная модель доступа
Фундамент разграничения доступа в ИС. Разделяет систему на три сущности:
* **Субъекты (Активные):** Пользователи, приложения, внешние коммуникации.
* **Объекты (Пассивные):** Файлы, данные БД, системные ресурсы.
* **Процессы:** Действия субъектов над объектами.

> **Постановка задачи МБ:** Для каждой пары «субъект-объект» определить множество допустимых операций и контролировать их выполнение.

## 2. Дискреционные модели безопасности (DAC)
Основаны на **матрице доступа**, где строки — субъекты (или пользователи/группы), столбцы — объекты, а ячейки — разрешенные операции (`r` — чтение, `w` — запись, `e` — выполнение).

### Подходы к организации матрицы:
1. **Централизованный:** Матрица хранится как отдельный самостоятельный объект.
2. **Распределенный:** Разделяется на **списки доступа (ACL)** у объектов или **списки возможностей (Capabilities)** у субъектов.

### Подходы к управлению:
* **Принудительное (ПУД):** Права жестко и централизованно задает только администратор.
* **Добровольное (ДУД):** Права определяет владелец объекта (тот, кто его создал). Реализует децентрализацию.

### Модель Харрисону-Руззо-Ульмана (HRU)
Доказывает теоретические ограничения DAC:
* Поведение систем на основе произвольной модели HRU с точки зрения безопасности **алгоритмически неразрешимо (непредсказуемо)**.
* Существует проблема «гуляющих прав» и уязвимость перед **«Троянскими программами»** (нет контроля за порождением информационных потоков).

### Пример концепта Матрицы доступа на Python
```python
# Упрощенная демонстрация проверки прав в DAC
matrix_access = {
    "Иванов":  {"Table_1": ["READ", "WRITE"], "Table_2": []},
    "Петров":  {"Table_1": ["READ"],          "Table_2": ["READ", "WRITE", "CREATE"]},
    "Сидоров": {"Table_1": ["READ", "WRITE", "CREATE", "DELETE"]}
}

def check_access(user, table, action):
    user_rights = matrix_access.get(user, {}).get(table, [])
    if action in user_rights:
        print(f"Доступ РАЗРЕШЕН: {user} -> {action} над {table}")
        return True
    print(f"Доступ ЗАПРЕЩЕН: {user} -> {action} над {table}")
    return False

# Проверка
check_access("Иванов", "Table_1", "WRITE")  # Разрешено
check_access("Иванов", "Table_2", "WRITE")  # Запрещено
```

## 3. Мандатные модели безопасности (MAC)
Основаны на **метках конфиденциальности (уровнях секретности/доступа)**. Главная цель — предотвратить утечку информации «сверху вниз» (из закрытых источников в открытые).

### Классическая модель Белла-ЛаПадулы
Базируется на двух неукоснительных правилах:
1. **Простая безопасность (NRU — No Read Up):** Субъект не может читать объект с более высоким уровнем безопасности (FL(s) ≥ FL(o)).
2. **Свойство `*` (NWD — No Write Down):** Субъект не может записывать данные в объект с более низким уровнем безопасности (FL(o) ≥ FL(s)).

* **Плюс:** Если начальное состояние безопасно и правила переходов соблюдены, то любое последующее состояние системы гарантированно безопасно (Основная теорема безопасности).
* **Минус:** Избыточность прав внутри одного класса. Часто дополняется дискреционным подходом внутри уровня.

## 4. Ролевые модели управления (RBAC)
Решают проблему сложности администрирования при большом количестве пользователей. Вместо связи *Пользователь ↔ Объект* вводится промежуточная сущность — **Роль** (должность/функция).

* Количество связей становится пропорциональным **сумме**, а не произведению количества пользователей и объектов.
* Права выдаются по принципу **минимизации привилегий** (только то, что необходимо для обязанностей).
* **Сеанс работы:** Пользователь в рамках сеанса активизирует подмножество доступных ему ролей.

### Разновидности RBAC:
* С иерархической организацией ролей (наследование прав).
* Статическое распределение обязанностей (взаимоисключающие роли на уровне системы для исключения сговора).
* Динамическое распределение обязанностей (взаимоисключающие роли в рамках одного сеанса).

### 📝 Пример реализации RBAC в реляционных СУБД (SQL)
```sql
-- 1. Создание ролей
CREATE ROLE db_administrator;
CREATE ROLE db_manager;
CREATE ROLE db_operator;

-- 2. Назначение прав (полномочий) для ролей на объекты (таблицы)
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE orders TO db_manager;
GRANT SELECT ON TABLE orders TO db_operator;

-- 3. Назначение ролей конкретным пользователям
GRANT db_manager TO ivanov_user;
GRANT db_operator TO petrov_user;

-- Пример создания иерархии (Менеджер наследует права Оператора)
-- (Зависит от СУБД, концептуальный пример):
GRANT db_operator TO db_manager; 
```

## 5. Индивидуально-групповое разграничение доступа
Упрощенная и наиболее распространенная на практике разновидность ролевой модели.
* Пользователи объединяются в **рабочие группы**.
* При входе в систему пользователь **автоматически и одновременно** получает как свои личные права, так и права всех групп, в которые он входит.
* Права суммируются: $R \subseteq \{A[u, o] \cup A[g_1, o] \cup A[g_2, o] \dots\}$.
* Как и в DAC, здесь нет строгого математического доказательства безопасности системы «из коробки», но модель сильно упрощает проектирование.
