# Триггеры в MS SQL Server

**Триггер** – это специальный тип откомпилированных хранимых процедур, выполнение которых автоматически обусловлено наступлением определенных событий внутри реляционной базы данных.

### Ключевые особенности:
* Не имеет входных или выходных параметров.
* Становится «одним целым» (единой транзакцией) с вызвавшей его операцией.
* Запускается автоматически, в отличие от обычных процедур, которые нужно вызывать явно (`CALL`/`EXEC`).

---

## 1. Классификация триггеров в SQL Server

1. **DML-триггеры** — срабатывают при попытке изменения данных в таблицах или представлениях (события `INSERT`, `UPDATE`, `DELETE`).
2. **DDL-триггеры** — активизируются при изменении структуры БД (события `CREATE`, `ALTER`, `DROP`).
3. **Logon-триггеры** — выполняются в ответ на событие `LOGON` при установке пользовательского сеанса с экземпляром SQL Server.

---

## 2. Назначение DML-триггеров

### Когда триггеры необходимы:
* **Сложные ограничения:** проверка корректности данных и бизнес-правил, которые невозможно реализовать с помощью стандартных ограничений `CHECK` или `UNIQUE`.
* **Аудит и журнализация:** фиксация сведений о внесенных изменениях, авторе изменений и времени операции во внешних таблицах безопасности.
* **Каскадные воздействия:** автоматическое изменение связанных данных в других таблицах, если это нельзя настроить декларативно через `FOREIGN KEY`.
* **Вычисление производных данных:** автоматический пересчет и обновление агрегированных значений при изменении связанных строк.

### Когда триггеры использовать НЕ стоит:
* Не заменяйте триггерами базовую декларативную ссылочную целостность (`FOREIGN KEY`) или проверочные ограничения (`CHECK`).
* Избегайте сложных цепочек триггеров, способных вызвать рекурсию.

> **Рекурсия бывает двух видов:**
> * **Прямая:** Триггер на Таблице 1 изменяет саму Таблицу 1, вызывая себя повторно.
> * **Косвенная:** Триггер на Таблице 1 изменяет Таблицу 2 \(\rightarrow\) срабатывает триггер Таблицы 2 и изменяет Таблицу 1.

## 3. Временные таблицы `inserted` и `deleted`

В момент выполнения DML-операций в оперативной памяти сервера создаются две виртуальные таблицы. Они имеют точно такую же структуру (колонки и типы данных), как и целевая таблица триггера.

| Операция | Таблица `inserted` | Таблица `deleted` |
| :--- | :--- | :--- |
| **`INSERT`** | Содержит новые добавленные строки. | **Пустая**. |
| **`DELETE`** | **Пустая**. | Содержит копии удаленных строк. |
| **`UPDATE`** | Содержит новые (измененные) значения строк. | Содержит старые значения строк (до изменения). |

---

## 4. Сравнительный анализ: AFTER против INSTEAD OF

| Критерий | Триггеры `AFTER` (или `FOR`) | Триггеры `INSTEAD OF` |
| :--- | :--- | :--- |
| **Где создаются** | Только в **таблицах**. | В **таблицах** и **представлениях (VIEW)**. |
| **Количество** | Несколько триггеров на одно и то же событие. | Строго **один** триггер на одно событие (`INSERT`, `UPDATE` или `DELETE`). |
| **Время выполнения** | После успешного завершения операции, каскадных действий и проверок ограничений. | **Вместо** выполнения основной операции. Основной запрос переопределяется логикой триггера. |
| **Ограничения** | Нет жестких ограничений. | Нельзя определять для таблиц, на которые распространяются каскадные ограничения ссылочной целостности. |

### Управление порядком `AFTER`-триггеров
Если для таблицы создано несколько триггеров одного типа, их последовательность произвольна. Однако можно явно назначить первый и последний триггеры с помощью системной процедуры:
```sql
EXEC sp_settriggerorder @triggername = 'MyTrigger', @order = 'first', @stmttype = 'INSERT';
EXEC sp_settriggerorder @triggername = 'AnotherTrigger', @order = 'last', @stmttype = 'INSERT';
```

## 5. Базовый синтаксис DDL-операций

### Создание DML-триггера (`AFTER INSERT`)
```sql
CREATE TRIGGER Purchasing.LowCredit 
ON Purchasing.PurchaseOrderHeader 
AFTER INSERT 
AS 
BEGIN
    DECLARE @creditrating TINYINT, @vendorid INT;

    SELECT @creditrating = v.CreditRating, @vendorid = p.VendorID 
    FROM Purchasing.PurchaseOrderHeader p  
    JOIN inserted i ON p.PurchaseOrderID = i.PurchaseOrderID 
    JOIN Purchasing.Vendor v ON v.VendorID = i.VendorID;

    IF @creditrating = 5 
    BEGIN
        -- Генерируем пользовательскую ошибку и отменяем транзакцию
        RAISERROR ('Рейтинг поставщика слишком низкий.', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

### Создание DDL-триггера (Защита схемы базы данных)
Действует на уровне всей БД (`DATABASE`) или всего сервера (`ALL SERVER`). Не создает таблицы `inserted`/`deleted`.
```sql
CREATE TRIGGER safety 
ON DATABASE 
FOR DROP_TABLE, ALTER_TABLE 
AS 
BEGIN
    PRINT 'Вы должны отключить триггер "safety" перед удалением или изменением таблиц!';
    ROLLBACK; -- Откат DDL-операции
END;
```

### Управление состоянием триггеров
```sql
-- Изменение структуры
ALTER TRIGGER trigger_name ON table_name AFTER UPDATE AS ...

-- Включение / Выключение триггера
DISABLE TRIGGER safety ON DATABASE;
ENABLE TRIGGER safety ON DATABASE;

-- Включение / Выключение ВСЕХ триггеров таблицы
DISABLE TRIGGER ALL ON table_name;

-- Удаление
DROP TRIGGER safety ON DATABASE; -- для DDL
DROP TRIGGER trigger_name;        -- для DML
```

## 6. Обработка исключений и системные функции

При возникновении ошибки или вызове `ROLLBACK` внутри триггера происходит автоматический откат всей транзакции, и выполнение инструкции прерывается.

Для генерации ошибок используется функция `RAISERROR('текст', Severity, State)`, где:
* `Severity` (Серьезность): число от 0 до 25. Уровни с 20 по 25 считаются неустранимыми (обрывают соединение с клиентом).
* `State` (Состояние): целое число от 0 до 255 для идентификации конкретного места возникновения ошибки в коде.

### Системные функции для обработки в блоке `TRY...CATCH`:
* `ERROR_LINE()` — номер строки, на которой произошел сбой.
* `ERROR_MESSAGE()` — полный текст сообщения об ошибке.
* `ERROR_NUMBER()` — уникальный код ошибки.
* `ERROR_PROCEDURE()` — имя триггера или хранимой процедуры, где возникла ошибка.
* `ERROR_SEVERITY()` и `ERROR_STATE()` — уровень серьезности и состояние ошибки соответственно.
